## Shape
1. **Data contract.** Mail is the Email Cell's twin format v1 (`cell/twin/schema.mjs`). People and companies come from the shared synthetic twin `demo-twin` proposed by mail.dev.a (`people/`, `orgs/`, `mail/`, `drafts/`). The CRM owns only `crm/` inside it:
   - `crm/leads/<org-id>.json` (`crm.lead/1`): one row per company: stage, owner, next step, next-step date, notes ref. Draft state and last contact are derived, not stored: draft state from `drafts/`, last contact from `mail/index/correspondents.json` and threads.
   - `crm/stages.json` (`crm.stages/1`): the pipeline's stages in order.
   - `crm/links/<thread-id>.json` (`crm.link/1`): a mail thread tied to a lead (and person), so a thread opens its CRM row and a row lists its threads.
   - `crm/follow-ups.json` is derived: leads whose last outbound message has no reply in 5 days.
   These names are a proposal until I have read the team CRM's code (`crm/`, `crm/follow-ups/`) and account C's deck; I will align to their shapes rather than add a third.
2. **Synthetic generator**, seeded the same as mail.dev.a's, writing only `crm/`. Reserved domains only (example.com/.org/.net).
3. **Site**: static pages, no server, no connector. Lead board, a company's page (people, threads, drafts, next step), contacts, follow-ups. It reads a vault in the browser through sgit's vault library, as the Email Cell's `/app/connect.html` does.
4. **Demo mode**: always on a button; it loads the public synthetic vault and labels every screen "Synthetic demo".
5. **Real mode**: the user's own vault key, entered only in their browser and kept sealed there. The site never holds real data; private mail stays on the Web Summit side (G4).
6. **Tests** in Node for the generator, the derivations (last contact, follow-ups) and the link checks; a Chromium check of each page against the synthetic vault.
