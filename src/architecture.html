Architecture: the website, the vault, and the twin

Two places hold everything. The public website and repository hold how the cell works: code, plan, policy and made-up test mail. The user's own vault holds the mailbox itself: the twin, the lanes, and the signed policies. Real mail never touches the public side.

Status, 16 November 2026: the code runs against a simulated mailbox only. Items in grey italics are a plan. Written by cell.email@AgentiCCells.dinis for Dinis Cruz.

1. Where everything lives

Solid arrows carry the mailbox's data. Dashed arrows carry only code and configuration: nothing flows back from the vault or Gmail into the public repository.

On the website and repository

  • How the cell works: the plan, the policy, the code, the tests.
  • Templates for the policy files, with example values.
  • A made-up mailbox to test against.
  • Public by design: anyone can read how it works and check the rules.

In the user's vault

  • The twin: every message, thread, label and attachment.
  • The lanes: every proposal, approval, read and send, signed.
  • The real policy files, signed by the person.
  • Owned and keyed by the user. We keep no copy.

Only with the gateway

  • The Google OAuth client secret and refresh token.
  • Nothing else holds them: not agents, not the CRM app, not this build session.

3. How I am thinking about the twin

Gmail delivers; the twin is where work happens

Gmail stays the source of truth for what was delivered and sent. The twin is the source of truth for everything we do with it: reading, triage, drafting, approving, and the record of who did what. Sync runs one way, in. Changes go back only as signed, approved actions that the gateway checks against the policy.

Layers, from facts to intent

The raw message is a fact and is never edited. The clean copy is a safe view of that fact. The indexes are derived and can always be rebuilt. The lanes are intent: what people and agents want to happen. Keeping these apart is what lets us rebuild, audit and replay.

The user owns it, so it is also a backup

Because the twin lives in a vault the user creates and keys, it is their own capture of their mailbox. If a Gmail account is lost, closed or suspended, the user still holds every message, versioned. That is a feature in its own right, not a side effect.

The twin keeps agents away from the source

Agents never see Gmail and never see raw mail. They see the clean copy and can only propose. That is the air gap the article asks for: reading an email can never, by itself, send one.

Drift, and how we notice it

The gateway records Gmail's history cursor with each sync and re-checks on a timer, because push notices can be late or lost. If the twin falls behind, the policy fails closed: every recipient counts as a first contact until it catches up.

Decided by Dinis, 16 November 2026

  • Deleted messages stay in the backup. A deletion in Gmail is recorded in the twin; the message's file is kept.
  • Labels stay 100% in sync with Gmail, both ways: label changes in Gmail come into the twin, and approved label changes in the twin go back to Gmail (this needs the gmail.modify scope).
  • Still open: whether raw/ and clean/ are one vault or two.

4. One email, start to finish

  1. Arrives. Gmail tells the gateway something changed; the gateway reads the change and writes the message to raw/. plan
  2. Made safe. The firewall writes the clean copy to clean/ and marks it clean, suspicious or hostile. built (simulation)
  3. Read. The drafter reads the clean copy; its read is a signed entry on the reads lane. built (simulation)
  4. Proposed. The drafter proposes a reply on the actions lane, signed with its key. built (simulation)
  5. Approved. A person signs an approval, or a signed automation covers it (fixed template, verified correspondent, clean message). built (simulation)
  6. Checked. The gateway verifies the lanes and the signed policies, then runs the email policy: recipients, language, template, rates, first contact, data loss, kill switch. built (simulation)
  7. Sent. The gateway sends through Gmail and writes the result to the outbox lane. plan
  8. Recorded. The sent message syncs back into raw/; the CRM matches it to its draft by reference. plan
